# Epic: Synonyms & Plural Forms

## Smarter Related Words (Synonyms) + Structured Plural Forms

> **Epic Number:** LC-130 (continuing from LC-122 Tiered AI Routing)
> **Feature Area:** `libs/shared/domain/`, `apps/api/src/import/`, `apps/api/src/cards/`, `features/vault/`, `features/review/`, `features/listen/`
> **Depends on:** Word enrichment pipeline (`word-enrich.service.ts`, `word-enrich-prompt.builder.ts`), card creation (`cards.service.ts`), add-word sheet, word-detail page, review player, listen player
> **Design reference:** `design-reference-synonyms-plurals.html` (open in a browser before building any screen)

---

## TL;DR — what we are changing and why

Two related-but-separable quality problems with our vocabulary cards:

1. **"Related words" are not actually related.** Today they are derived client-side by
   matching the first four characters of the German word against other cards in the user's
   own vault. The result is orthographic noise — `das Flugzeug` surfaces `das Hobby`,
   `das Café`, and `das Buch` (see current screenshots) because they happen to share letters
   or are simply other `das` nouns nearby. None of these are synonyms. We want related words
   to be **true synonyms** of the headword, generated by the AI enrichment pipeline and
   stored on the card, each with its own translation **and example sentence** so the learner
   sees the synonym used in context.

2. **Plural forms are unstructured.** The plural is sometimes informally embedded in the
   `back` string using the dictionary convention (`Flugzeug, -e`) and sometimes mentioned
   in free-text `notes` ("Plural: die Hunde."). It is never a queryable field, is missing on
   most cards, and is never generated at creation/import time. Pedagogically, every credible
   German resource says the same thing: **learn the noun together with its article and its
   plural from day one.** We want a structured `plural` field, generated at creation/import
   time, and surfaced on the card detail page and in review.

## Current state (investigation findings)

### How related words are derived today

`features/vault/pages/word-detail/word-detail.component.ts` computes related words entirely
on the client with no semantic notion of relatedness:

```typescript
readonly relatedWords = computed(() => {
  const card = this.card();
  if (!card) return [];
  const word = card.content.back.toLowerCase();
  const stem = word.slice(0, 4);
  return this.cardStore.cards()
    .filter(c => c.id !== card.id)
    .filter(c => {
      const other = c.content.back.toLowerCase();
      return (other.includes(stem) || word.includes(other.slice(0, 4)))
        && Math.abs(other.length - word.length) <= 5;
    })
    .slice(0, 5);
});
```

Problems:
- **Not semantic.** First-4-character stem matching finds words that *look* alike, not words
  that *mean* alike. `Flugzeug` → `Flug...` matches nothing meaningful, so the length filter
  alone lets through arbitrary nearby `das`/short cards.
- **Vault-limited.** It can only ever surface words the user already has, so a synonym the
  user has never added can never appear.
- **No translations beyond what the matched card happens to have**, and **no example
  sentence** for the related word.

There is **no `relatedWords`/`synonyms` field** anywhere in `CardContent`
(`libs/shared/domain/src/index.ts`), and **no synonym generation** in the AI enrichment
pipeline (`word-enrich-prompt.builder.ts` asks only for
`back, front, article, categoryName, exampleTarget, exampleNative, confidence`).

### How plurals are handled today

- **No `plural` field** in `CardContent`.
- The plural ending is sometimes packed into `back` (`"Flugzeug, -e"`, `"Buch, ¾er"`) — this is
  the German dictionary convention and is the string shown in the vault list and review card.
- Free-text `notes` sometimes contains "Plural: die Hunde." but this is inconsistent and
  unparseable.
- The enrichment prompt never requests a plural, and the manual add-word form has no plural
  input.

## Design principles (UI/UX research)

Backed by cognitive-science findings on vocabulary acquisition and standard German pedagogy:

1. **Always teach the noun with its article and plural together.** Every reputable German
   resource (Goethe-aligned guides, Mango, FluentU, German-with-Laura) gives the same
   advice: memorize `der Tisch, die Tische` as one unit, never `Tisch` alone. So the plural
   belongs *next to the headword*, not buried in notes. We surface it as a quiet secondary
   line under the headword (e.g. `Plural: die Flugzeuge`) on the detail page, and on the
   review card's revealed (back) face — where recall is being tested.

2. **Synonyms must come with context.** Research on retention (contextual usage + spaced
   recall beats rote lists) and the strongest vocab apps (Brainscape, FlashcardLab) pair each
   synonym with a translation *and* a sample sentence. A bare synonym list teaches
   substitution without nuance; a synonym + example teaches *when* to use it. So each synonym
   is `{ word, article, translation, example }`.

3. **Don't overload the review card.** The review back face is a recall surface; piling
   synonyms onto it dilutes the test. Plurals belong there (they are part of the word's
   identity); synonyms do **not** appear during active review — they live on the detail page
   and (compactly) in the Listen queue, which is a browsing/exposure surface.

4. **Progressive disclosure on detail.** The detail page already uses stacked cards
   (header → mastery → examples → notes → related). We upgrade the "Related Words" card into a
   "Synonyms" card where each row can expand to reveal its example sentence, so the default
   view stays scannable.

5. **Graceful absence.** Many words have no good synonym (proper-ish nouns, function words)
   and non-nouns have no plural. Every new surface must render cleanly when the field is
   empty — no empty headers, no "—" noise.

6. **Backwards compatibility.** Hundreds of existing cards have neither field. New fields are
   optional; UI hides absent data; a one-off backfill is a separate, optional ticket.

## Data model: target shape

```typescript
// libs/shared/domain/src/index.ts

export interface Synonym {
  /** The synonym headword in the target language, WITHOUT article (e.g. "Maschine"). */
  word: string;
  /** Grammatical article of the synonym, or null for non-nouns. */
  article: ArticleType | null;
  /** Native-language translation of the synonym. */
  translation: string;
  /** A natural target-language sentence using the synonym. May be ''. */
  example: string;
  /** Native-language translation of the example. May be ''. */
  exampleNative: string;
}

export interface CardContent {
  front: string;
  back: string;
  article: ArticleType | null;
  gender: GenderType;
  /** NEW — plural form of the noun INCLUDING its article, e.g. "die Flugzeuge".
   *  null for non-nouns or when unknown. */
  plural: string | null;
  examples: ExampleSentence[];
  /** NEW — true synonyms of the headword, generated by AI enrichment. Defaults to []. */
  synonyms: Synonym[];
  notes: string;
  audioAssetId: string | null;
  imageUrl: string | null;
  phonetic: string | null;
}
```

Both fields are optional/defaulted everywhere so old cards keep working.

**Phase:** 1 — Backend AI
**Points:** 3
**Depends on:** LC-130

#### User story

As a learner importing words, I want each generated card to include true synonyms and the
correct plural, so my vault teaches me words in context from the start.

#### Files to modify

| File | Change |
|---|---|
| `apps/api/src/import/word-enrich-prompt.builder.ts` | Request `plural` + `synonyms` per word |

#### Prompt changes

Extend the per-word output contract. The critical instruction is the definition of "synonym"
— the model must return **words with the same or very close meaning**, NOT word-family
members, NOT orthographic neighbours, NOT translations.

```typescript
build(words: RawExtractedWord[], targetLanguage: string, nativeLanguage: string): string {
  const wordList = words.map((w, i) => `${i + 1}. "${w.back}"`).join('\n');

  return `
You are a language learning assistant generating flashcard content.

WORDS TO ENRICH (${targetLanguage}):
${wordList}

For each word above, output a JSON array where each element has EXACTLY these fields:

- "back": copy the word EXACTLY as listed above. Do NOT add or prepend any article.
- "front": the ${nativeLanguage} translation of the bare word
- "article": "der", "die", "das", or null. Derive from your own knowledge.
- "plural": for nouns, the FULL plural form INCLUDING the plural article, e.g. "die Flugzeuge".
    For non-nouns (verbs, adjectives, adverbs, phrases) use null.
    The plural article in ${targetLanguage} is always "die" for German.
- "categoryName": one of [${CATEGORIES.join(', ')}]
- "exampleTarget": a natural ${targetLanguage} sentence using the word.
- "exampleNative": ${nativeLanguage} translation of that sentence.
- "synonyms": an array of 0–3 TRUE SYNONYMS — words with the SAME or VERY CLOSE meaning,
    interchangeable in most contexts. NOT word-family members, NOT related concepts,
    NOT words that merely look similar. If there is no good synonym, return [].
    Each synonym element has EXACTLY:
      - "word": the synonym in ${targetLanguage}, WITHOUT article
      - "article": "der"/"die"/"das"/null
      - "translation": ${nativeLanguage} translation of the synonym
      - "example": a natural ${targetLanguage} sentence using the synonym
      - "exampleNative": ${nativeLanguage} translation of that sentence
- "confidence": 1.0

SYNONYM RULES (critical):
- A synonym must be substitutable for the headword with no change in core meaning.
  Good: "Flugzeug" → "Maschine", "Flieger". Bad: "Flugzeug" → "Flughafen" (related, not synonym).
- Prefer common, learner-useful synonyms over rare/archaic ones.
- Never list the headword itself as its own synonym.
- 0 synonyms is correct and expected for many words. Do not invent weak ones.

Return ONLY the JSON array. No markdown. No preamble. No extra fields.
`.trim();
}
```

#### Acceptance criteria

- [ ] Prompt requests `plural` and `synonyms` with the exact sub-shape
- [ ] Prompt contains explicit, example-driven "what is / is not a synonym" guidance
- [ ] Prompt instructs the model to return `[]` synonyms rather than weak guesses
- [ ] Non-nouns get `plural: null`
- [ ] Existing fields are unchanged in name and meaning

### LC-132 · Parse & validate synonyms + plural in `WordEnrichService`

**Phase:** 1 — Backend AI
**Points:** 3
**Depends on:** LC-131

#### User story

As a developer, I want enrichment responses parsed and defensively validated, so malformed
AI output never crashes import and never stores garbage synonyms.

#### Files to modify

| File | Change |
|---|---|
| `apps/api/src/import/word-enrich.service.ts` | Extend `parseEnrichmentResponse()`; extend `ImageExtractedWord` mapping |
| `libs/shared/domain/src/index.ts` | Add `plural` + `synonyms` to `ImageExtractedWord` |

#### Implementation

```typescript
private parseEnrichmentResponse(raw: string): ImageExtractedWord[] {
  const items = recoverJsonArray(raw);
  return items
    .map(item => ({
      front:         String(item['front'] ?? ''),
      back:          String(item['back'] ?? ''),
      article:       this.parseArticle(item['article']),
      plural:        this.parsePlural(item['plural'], this.parseArticle(item['article'])),
      categoryName:  String(item['categoryName'] ?? 'Other'),
      exampleTarget: String(item['exampleTarget'] ?? ''),
      exampleNative: String(item['exampleNative'] ?? ''),
      synonyms:      this.parseSynonyms(item['synonyms'], String(item['back'] ?? '')),
      confidence:    typeof item['confidence'] === 'number' ? item['confidence'] : 1.0,
    }))
    .filter(w => w.back.length > 0);
}

/** plural is only meaningful for nouns (article present). Drop for non-nouns. */
private parsePlural(value: unknown, article: ArticleType | null): string | null {
  if (!article) return null;
  const s = typeof value === 'string' ? value.trim() : '';
  return s.length > 0 ? s : null;
}

private parseSynonyms(value: unknown, headword: string): Synonym[] {
  if (!Array.isArray(value)) return [];
  const headLower = headword.toLowerCase().replace(/^(der|die|das)\s+/, '');
  return value
    .map(s => ({
      word:          String(s?.['word'] ?? '').trim(),
      article:       this.parseArticle(s?.['article']),
      translation:   String(s?.['translation'] ?? '').trim(),
      example:       String(s?.['example'] ?? '').trim(),
      exampleNative: String(s?.['exampleNative'] ?? '').trim(),
    }))
    // Reject empties and self-references (model occasionally echoes the headword)
    .filter(s => s.word.length > 0 && s.word.toLowerCase() !== headLower)
    .slice(0, 3);
}
```

#### Acceptance criteria

- [ ] `ImageExtractedWord` carries `plural: string | null` and `synonyms: Synonym[]`
- [ ] Malformed `synonyms` (non-array, missing fields) degrade to `[]`, never throw
- [ ] Self-referential synonyms (== headword) are filtered out
- [ ] Synonyms capped at 3
- [ ] Plural forced to `null` for non-nouns regardless of model output
- [ ] Empty plural string stored as `null`

## Phase 5 — Backfill & Sync

### LC-144 · Optional batch backfill of plural + synonyms for existing cards

**Phase:** 5 — Backfill
**Points:** 3
**Depends on:** LC-131, LC-132

#### User story

As an existing user, I want my old cards to gain plurals and synonyms without re-importing,
so the feature applies retroactively.

#### Files to modify

| File | Change |
|---|---|
| `apps/api/src/import/*` | Admin/maintenance route or script that finds cards with `plural == null && synonyms empty`, runs them through batch enrichment, and patches only the new fields |

#### Behaviour

- Process in throttled batches (reuse the 10-word batching + inter-batch delay).
- **Only fill empties** — never overwrite a user-edited plural/synonym or any other field.
- Idempotent and resumable; safe to run repeatedly.

#### Acceptance criteria

- [ ] Backfill only touches `plural` + `synonyms`, never `front/back/article/examples/notes`
- [ ] Skips cards that already have the data
- [ ] Respects rate limits; resumable
- [ ] Dry-run mode logs what would change without writing

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Model returns weak/related-but-not-synonym words | Strong prompt with positive+negative examples (LC-131); prefer `[]` over weak guesses; cap at 3; self-reference filter (LC-132) |
| Plurals wrong for irregular nouns | Use Haiku (already the enrichment model, strong on German); store full plural-with-article so display is never recomputed; users can edit (LC-136) |
| Extra tokens per word increase cost | Synonyms capped at 3; plural is short; enrichment already uses cheap Haiku (~$0.005/batch). Monitor with existing token logging |
| Old cards look inconsistent (some have data, some don't) | Optional backfill (LC-144); UI degrades gracefully everywhere |
| Review card clutter | Synonyms deliberately excluded from review; only plural added (design principle 3) |
